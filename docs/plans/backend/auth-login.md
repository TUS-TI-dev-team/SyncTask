# POST auth/login 開発計画

## 1. 目的と完了条件

`docs/design/` の仕様に基づき、未認証で利用できる `POST /api/auth/login` をテスト先行で実装する。

完了条件は次のすべてを満たすこととする。

- `backend/TESTING_GUIDE.md` に従った単体テストを作成している。
- `go test ./...` がすべて成功する。
- `go test -cover ./...` で、今回追加・変更するログイン関連の `handler`、`service`、`repository`、`model`、`util`、`router` 各パッケージが 80% 以上である。
- `go test -coverprofile=coverage.out ./...` と `go tool cover -func=coverage.out` でも全体値を記録する。起動処理・マイグレーション・自動生成Swaggerを含む `main`、`db`、`docs` は今回の80%判定対象外とする。
- APIレスポンス、Cookie、DB更新、ログ記録、レート制限、アカウント列挙防止が設計仕様と一致する。
- `go test -race ./...` が成功する。

## 3. 実装前に確定する設計判断

既存バックエンドには `handler`、`service`、`repository`、`model`、`util` の各層、Router内のDI、共通エラー形式が導入済みである。ログイン機能もこの構成・命名・手動モック方式へ合わせる。ログイン処理はDBトランザクションと時刻・乱数・遅延に依存するため、既存構成を保ちながら単体テスト可能な依存境界を追加する。

想定する構成は次のとおり。実際の名称は実装開始前に既存変更を再確認して確定する。

- `backend/handler/login.go`: JSONデコード、クライアントIP取得、サービス呼び出し、`model.AppError` の共通JSON変換、Cookie/`Retry-After` 出力、Swaggerコメント。既存Handlerと同様に `service.LoginService` を受け取る。
- `backend/service/login.go`: 評価順序、認証成否、失敗時の遅延調整、セッション/CSRFトークン生成、ユースケースの制御。
- `backend/repository/login.go`: `repository.LoginRepository` インターフェースと `NewLoginRepository(*sql.DB)` を既存形式で定義する。SQLとトランザクション、IP行・アカウント行のロック、失敗回数更新、旧セッション削除、新セッション追加、監査ログ追加を担当する。
- `backend/model/login.go`: リクエスト、レスポンス、ユーザー、内部認証結果の型と入力検証。既存の `model.AppError`、`model.ErrorDetail`、`model.NewErrorResponse` を再利用し、ログインに必要な429等の生成補助だけを `model/error.go` へ最小追加する。
- `backend/util/login.go`（または責務が明確な同等名）: メールアドレスの仕様どおりのtrim・小文字化、暗号学的乱数トークン生成など、独立して検証すべき処理を置く。検索用NFKC正規化の `NormalizeSearchText` はログインメールには使用しない。
- `backend/router/router.go`: 既存のTask DIと同じ位置でLogin Repository/Serviceを組み立て、`api.POST("/auth/login", ...)` を登録する。
- `backend/config/config.go` と `.env.example`: Cookieの `Secure` 切替、信頼済みプロキシ設定など、仕様を満たすために必要な設定だけを追加する。
- 必要に応じて `backend/db/migrations/000002_*.up.sql/.down.sql`: 現行スキーマと設計の不一致が見つかった場合のみ追加する。適用済みの `000001` は書き換えない。

外部依存は既存の標準ライブラリ、Gin、`database/sql`、`x/crypto`、`sqlmock`、testifyを優先する。ログIDには既に直接依存として導入されている `github.com/google/uuid` を再利用し、セッションIDとCSRFトークンにはUUIDではなく `crypto/rand` 由来の十分な長さのトークンを使用する。

変更後構成を確認した時点の基準値は、全テスト成功、`config 100.0%`、`handler 100.0%`、`model 92.9%`、`repository 91.7%`、`router 100.0%`、`service 86.7%`、`util 88.2%`、`main/db/docs 0.0%` である。ログイン追加後は既存品質を不必要に低下させず、変更対象パッケージごとに80%以上を維持する。

## 5. フェーズ1: テストデータ・単体テストの作成

### 5.1 テスト基盤

- 時刻を固定できるClock、セッショントークン/CSRFトークン生成器、パスワード照合器、失敗時Sleeperをインターフェースまたは関数として注入する。
- DBテストは `go-sqlmock` を用い、実DBに依存させない。トランザクションの開始、SQL順序、引数、commit/rollbackまで検証する。
- Handlerテストは既存の `mockTaskService` と同じ手動モック方式、Serviceテストは既存の手動Repositoryモック方式を採用する。Repositoryテストは `go-sqlmock` を用いる。
- HTTPテストは `httptest` とGin TestModeを使う。Ginモードを変更したテストは `t.Cleanup` 等で元の状態へ復元する。
- パスワード fixture は平文とbcryptハッシュを対応させる。ログやエラーに平文、ハッシュ、Cookie値が露出しないことも確認する。
- 時刻はJSTの固定値、ユーザーID・ログID・トークンは固定値を返すfakeで再現可能にする。
- テスト名は `正常系:`、`異常系:`、`境界値:`、`準正常系:` の日本語形式とし、実装の `@spec` と対応させる。

### 5.2 初期テストデータ

- 有効アカウント: 正規化後メール、bcrypt済みパスワード、失敗回数0、ロックなし。
- 境界アカウント: 失敗4回、最終失敗が15分未満、次回失敗で30分ロック。
- リセット対象アカウント: 最終失敗から15分超過し、次の失敗を1回目として扱う。
- ロック中アカウント: 正しいパスワードでも401となる状態。
- 論理削除済み相当: 正規化メール検索では未登録と同じ結果になる状態。
- IP制限: 29回失敗、30回目で15分遮断、遮断中、最終失敗から5分超過の各状態。
- 既存セッションあり/なし、期限切れセッションCookie、未知のセッションCookie。
- 入力: emailの半角・全角空白/タブ/改行、password長8/128、欠落、null、型違反、不正JSON、未知フィールド、複数JSON値。

### 5.3 初期テストケース候補

#### Handler / Router

- 正常系: `/api/auth/login` が登録され、正規化可能な入力で200を返す。
- 正常系: 成功レスポンスが設計どおりの `user` フィールドを返す。
- 正常系: `sync_task_sid` と `XSRF-TOKEN` の名前、値、Path、SameSite、Max-Age、HttpOnly差分、環境別Secure属性が正しい。
- 正常系: メール前後の半角・全角スペース、タブ、改行を除去し、小文字化する一方、passwordは変更しない。
- 異常系: JSON不正、ボディ欠落、必須値欠落、null、型違反、password 7文字/129文字を400 `BAD_REQUEST` とし、`details` を必ず配列で返す。
- 異常系: 入力検証エラーではSleeper、認証失敗カウンター更新、`LOGIN_LOG` を実行しない。ただし `ACCESS_LOG` は記録する。
- 異常系: 認証失敗は401 `UNAUTHORIZED`、IP遮断中は429 `RATE_LIMIT_EXCEEDED` と正しい `Retry-After` を返す。
- 境界値: password 8文字/128文字を受理する。
- 準正常系: `Content-Type`、Cache-Control、Pragmaおよび既存の共通セキュリティヘッダー方針との整合を検証する。
- 準正常系: 信頼済みプロキシ設定時のみ転送元IPを採用し、任意の転送ヘッダーを無条件に信用しない。

#### Service

- 正常系: パスワード一致かつ未ロック時に失敗状態をリセットし、旧Cookie対応セッションだけを削除して新セッションを発行する。
- 正常系: 既存Cookieなし/未知Cookieでも成功し、他端末セッションを削除しない。
- 異常系: 未登録メールでもダミーハッシュを必ず照合して401を返す。
- 異常系: パスワード不一致、未登録、削除済み、アカウントロック中を同じ401本文にする。
- 異常系: アカウントロック中は正しいパスワードでも拒否し、IP失敗回数を加算する。
- 異常系: IP遮断中はアカウント照会より先に429とし、遮断期限の残秒を算出する。
- 境界値: アカウント5回目失敗で30分ロック、15分空いた失敗でカウンターをリセットして1にする。
- 境界値: IP 30回目失敗で15分遮断、5分空いた失敗でカウンターをリセットして1にする。
- 境界値: ロック/遮断の終了時刻ちょうどは再試行可能とする。
- 準正常系: 401/429の処理総時間が固定Clock/Sleeper上で1秒となり、既に上限を超えた場合は追加sleepしない。
- 異常系: トークン生成、DB更新、ログ保存など内部失敗時は500へ変換し、Cookieを発行しない。

#### Repository / Transaction

- 正常系: IP行とアカウント行を `FOR UPDATE` 相当で取得し、並行更新に耐える順序で処理する。
- 正常系: 成功時リセット、受信Cookieに対応する旧セッション削除、新セッション登録、`LOGIN_LOG`、`ACCESS_LOG` を同一トランザクションでcommitする。
- 異常系: 認証失敗時にアカウント/IPカウンターと両ログを原子的に更新する。
- 異常系: 未登録時もIPカウンター、`LOGIN_LOG(USER_ID=NULL)`、`ACCESS_LOG(USER_ID=NULL)` を記録する。
- 異常系: メールを確定できない入力エラーは `ACCESS_LOG` のみ記録する。
- 異常系: 各SQLエラーでrollbackし、部分的なセッション作成やカウンター更新を残さない。
- 準正常系: ログにpassword、ハッシュ、セッションID、CSRFトークンを渡さない。

#### Security / Side effects

- エラー本文から未登録、削除済み、ロック中を区別できない。
- 成功時だけCookieを発行し、400/401/429/500では認証Cookieを発行しない。
- 新セッションIDとCSRFトークンは受信値を再利用せず、互いに別の値を使用する。
- User-Agentを新しい `LOGIN_SESSION` に保存する。

## 6. フェーズ2: プログラム作成

1. `model/login.go` にログインモデルと入力検証を追加し、既存の共通エラー形式を拡張して再利用する。
2. Clock、Sleeper、TokenGenerator、PasswordVerifierの依存境界を実装する。パスワード照合はbcryptを使用し、未登録時にも固定の有効なダミーハッシュを照合する。
3. Repositoryを実装する。行ロックとトランザクションにより、同一メール・同一IPの並行失敗加算、成功時リセット、セッション差し替え、ログ保存を原子的に行う。
4. Serviceを仕様の評価順序どおり実装する。入力検証後にIP遮断、アカウントロックを含む認証、成功/失敗更新を行う。
5. Handlerを実装し、成功レスポンス、共通エラー、Cookie、`Retry-After`、キャッシュ抑止ヘッダーを出力する。
6. Routerの既存DI構成へLogin Repository/Serviceを追加して `POST /api/auth/login` を登録する。Cookie Secureや信頼済みプロキシ設定の注入が必要な場合は、`SetupRouter` の呼び出し元と既存Routerテストを同時に更新する。
7. 全ての公開処理と重要な内部処理に、事前条件・事後条件・エラー仕様を示す簡潔な `@spec` GoDocを付ける。
8. `gofmt` と、利用可能であれば `go vet ./...` を実行する。

実装中に設計書間の矛盾または未定義事項を発見した場合は、推測で外部仕様を決めず、具体的な選択肢と影響を提示してユーザーへ確認する。内部構造だけの変更で外部挙動に影響しない場合は、既存パターンに合わせて進める。

## 7. フェーズ3: テストとカバレッジ判定

`backend/` で次の順に実行する。

```bash
gofmt -w <今回変更したGoファイル>
go vet ./...
go test -v ./...
go test -race ./...
go test -coverprofile=coverage.out ./...
go tool cover -func=coverage.out
```

判定方法:

- 1件でもテスト失敗またはrace検出があればフェーズ4へ進む。
- 全テスト成功後、全体カバレッジとログイン関連各パッケージのカバレッジを記録する。
- ログイン関連の変更対象パッケージがすべて80%以上なら完了候補とし、全体値も参考値として変更差分、テスト結果、カバレッジ値、残存リスクとともにユーザーへ報告する。
- 自動生成ファイルや純粋なmain起動処理を分母から除外する必要がある場合は、恣意的に除外せず理由と計測方法を先にユーザーへ提示する。

## 8. フェーズ4: 失敗修正・カバレッジ追加の反復

### 8.1 テスト失敗時

1. 失敗を入力検証、認証判定、DB期待値、Cookie/レスポンス、時間依存、テスト不備に分類する。
2. 仕様とテストが正しい場合は、最小範囲でプログラムを修正する。
3. 仕様解釈またはテスト期待値が誤っていた場合は、変更理由と修正後ケースをユーザーへ示し、テスト変更の承認を得る。
4. 関連テストを先に実行後、フェーズ3の全コマンドへ戻る。

### 8.2 カバレッジ不足時

1. `go tool cover -func=coverage.out` と必要に応じてHTMLレポートで未到達分岐を特定する。
2. 単に数値を上げるケースではなく、未検証の仕様、エラー、境界値、副作用を洗い出す。
3. 追加候補ごとに、対象仕様、入力/fixture、期待結果、追加理由、想定カバレッジ効果をユーザーへ提示する。
4. ユーザーの明示的承認を得てからテストデータ・テストケースを追加する。
5. 追加テストが失敗した場合は8.1、成功した場合はフェーズ3へ戻る。

ユーザーの指示どおり、初期テストだけでなく、失敗修正に伴うテスト変更およびカバレッジ向上のためのテスト追加も、作成前に必ず判断を求める。

## 9. 実装時の重点確認事項

- APIパスは共通仕様に合わせて `/api/auth/login` とする。設計本文の `POST auth/login` はベースURL配下の相対パスとして扱う。
- emailは前後の半角・全角空白、タブ、改行のみを除去して小文字化し、passwordにはtrimやUnicode正規化を行わない。
- 入力不正は遅延・失敗カウンター加算なし。ただし `ACCESS_LOG` は記録する。
- 未登録でもbcryptのダミーハッシュ照合を行い、登録有無による処理時間差を抑える。
- メール単位ロック中でも正しいpasswordを拒否し、401本文を統一する。ロック中の追加試行で30分期限を延長しない。
- IP遮断中は429と整数秒の `Retry-After` を返し、遅延を適用する。遮断中試行のカウンター/期限更新有無は `04_login.md` の詳細フローに合わせる。
- 失敗応答は処理開始から `1.0s ± 0.1s`。テストでは実sleepせず注入したfakeで計算を検証する。
- 成功時は人工遅延を加えず、失敗カウンターをリセットするが、IPカウンターはリセットしない。
- 旧セッションは受信Cookieに対応する1件だけ削除し、他端末セッションを保持する。受信セッションIDを再利用しない。
- DB commit前にCookieを発行しない。失敗時はrollbackしてCookieなしの500とする。
- 本番HTTPSでは両CookieにSecureを付け、ローカル/テストでは設定により切替可能にする。`sync_task_sid` のみHttpOnlyとする。
- パスワード、ハッシュ、セッションID、CSRFトークンをレスポンス本文、監査ログ、アプリログへ出さない。
- `LOGIN_LOG` と `ACCESS_LOG` の記録条件を区別する。
