# チャンク削除処理における一時エラー発生時のリトライスコープおよびアドバイザリロック解放の振る舞い曖昧性

- **Status**: Resolved

- **Created At**: 2026-08-22 13:50:00
- **Target Files**:

## 1. 問題の概要
`job_design.md` 5-1 では、一時的エラー（DBタイムアウト、コネクション枯渇、デッドロック `40P01`）発生時に最大3回、指数バックオフ＋ジッターによるリトライを行うと規定されています。
しかし、4章のシーケンス図では「Advisory Lock 取得 → チャンク削除ループ（BEGIN → DELETE LIMIT 1000 → COMMIT） → Advisory Unlock」という全体の流れしか記載されておらず、**リトライのスコープが「失敗したチャンクの再試行」なのか「ジョブ全体（ロック取得から）の再試行」なのか**が曖昧です。
また、チャンク途中でエラーが発生してジョブが異常終了する場合に、保持中のアドバイザリロックが確実に解放されるフローが明記されていません。

## 2. 詳細な指摘内容
1. **リトライ粒度の曖昧さ**:
   チャンク分割削除（1,000件ごと）の途中でデッドロック等の一時エラーが発生した場合：
   - パターンA: 該当チャンクのトランザクションをロールバックし、アドバイザリロックを保持したまま同一チャンクの削除を最大3回リトライする。
   - パターンB: ジョブ全体を最初からリトライする。
   上記のどちらのスコープでリトライを適用するかが未定義です。パターンBの場合、既にコミットされた過去のチャンクは削除済みですが、ロックの再取得やバックオフ待機中のロック保持方針が問題となります。
2. **エラー終了時のロック解放の保証**:
   チャンクのリトライ上限到達時や恒久エラー発生時、例外によりジョブが途中脱出する場合に、`pg_advisory_unlock` が確実に実行されなければ、マルチインスタンス環境で他インスタンスの次回ジョブ実行が阻害されます。

## 3. 推奨される修正案
`job_design.md` の 5-1 および 4章シーケンス図に、以下のリトライ・ロック解放仕様を明確化してください。

1. **チャンク単位でのリトライ適用**:
   - 個別チャンクのトランザクション実行（`BEGIN` 〜 `DELETE` 〜 `COMMIT`）で一時エラー（デッドロック等）が発生した場合は、当該トランザクションを `ROLLBACK` した後、アドバイザリロックを保持した状態で最大3回まで指数バックオフ待機を挟んで同一チャンクの削除を再試行する。
2. **ジョブ異常終了と確実なアンロック**:
   - チャンクリトライが3回失敗した場合、またはリトライ不可の恒久エラーが発生した場合は、即座にループを中断し、`finally` / `defer` 節で `pg_advisory_unlock` を実行してロックを確実に解放した上で、構造化エラーログ（JSON）を出力してジョブを異常終了とする。
3. **シーケンス図の更新**:
   - チャンクループ内に `alt 一時エラー発生 -> ROLLBACK & retry (最大3回)` および `alt リトライ失敗 -> ROLLBACK & unlock & 構造化エラーログ出力` の分岐を明記する。

### 実施した修正内容
チャンク削除処理の一時エラー（デッドロック等）発生時のリトライスコープを「チャンク単位（最大3回指数バックオフ）」と明記し、3回失敗時または恒久エラー発生時には即座にジョブを中断して `defer` で確実にアンロックした上で構造化エラーログを出力する仕様を明確化しました。
