# パスワード変更 API の新パスワード入力検証におけるユーザー名・メールアドレスローカル部含有チェックの大文字小文字非区別 (Case-Insensitive) 明記漏れ

- **Status**: Resolved
- **Severity**: Medium
- **Created At**: 2026-08-17 17:05:00
- **Target Files**:
  - [03_users.md](docs/design/api_design/03_users.md)

## 1. 問題の概要
`03_users.md` の 3.2.4 節 (`PATCH users/{user_id}/password`) のリクエストパラメータテーブルにおいて、新パスワード (`new_password`) に対象ユーザーの「ユーザー名」および「メールアドレスのローカル部」を含めない制約が定義されていますが、この文字列比較時に「大文字・小文字を区別しない (Case-Insensitive)」比較を行う旨の明記が漏言しています。

## 2. 詳細な指摘内容
- **`03_users.md` L170 (3.2.4 Request Body テーブル `new_password`)**:
  > 8〜128文字。英大文字/英小文字/数字/記号のうち3種以上を含む。ログインセッション/DBから取得した対象ユーザーのユーザー名・メールアドレスのローカル部（4文字以上の場合）を新パスワード内に含まないこと。現在のパスワードと同一の場合は 422 エラー

### 問題点
1. **大文字・小文字の表記揺れによるバリデーション迂回リスク**:
   ユーザー名やメールアドレス（例: `User.Name@example.com` のローカル部 `user.name`）に対して、パスワード設定時に入力された `USER.NAME123!` や `User.Name123!` といった大文字・小文字を混ぜた新パスワードについて、実装者が `toLowerCase()` を行わずに `contains()` チェックを行うと、ポリシーの判定を容易に迂回できてしまいます。
2. **仕様の曖昧さ**:
   システム全体としてメールアドレスは一律小文字正規化される一方、パスワード含有チェック時の比較基準（Case-Sensitive か Case-Insensitive か）が明示されていないため、実装時・テスト時に判定基準のブレが発生します。

## 3. 推奨される修正案
`03_users.md` 3.2.4 節の `new_password` バリデーション説明文およびリクエスト評価順序ステップ 2 に、「大文字・小文字を区別せず（Case-Insensitive）判定すること」を明確に追記してください。
