## 1. 問題の概要
`02_auth.md` の OTP 検証 API 群（3.1.2 `register/verify-otp`, 3.1.7 `password-reset/verify-otp`, 3.1.11 `change-email/verify-otp`）において、記述されている「リクエスト評価順序（##### リクエスト評価順序）」と「エラー定義（##### Errors）」の間で、非 active ステータス（失効・検証済み・無効セッション）指定時の応答遅延（Timing Attack 対策）の適用有無に関して直接的な記述矛盾が存在します。

## 2. 詳細な指摘内容
1. **評価順序とエラー定義間の直接矛盾**:
   - 各 OTP 検証 API の「リクエスト評価順序」の「2. OTPセッション状態・期限検証」では、以下のように「**即座に返却**（遅延なし）」と明記されています：
     > 失効・既に検証済み等の非 `active` ステータスの場合は `400 Bad Request`（code: `"BAD_REQUEST"`）または `410 Gone`（code: `"GONE"`）を**即座に返却**します。
   - しかし、直後の「##### Errors」の `400 Bad Request` の項目では、以下のように「**ダミーセッション時も一律遅延 1.0s ± 0.1s**」と記載されています：
     > `- 400 Bad Request`: 入力形式違反（即時返却、遅延なし）または**無効なセッション/STATUS非active指定**またはOTP照合不一致（**試行1〜4回目。ダミーセッション時も一律遅延 1.0s ± 0.1s**、code: `"BAD_REQUEST"`）
2. **アカウント列挙・タイミング攻撃対策への影響**:
   - ダミーセッションや既に失効したセッションに対するリクエストにおいて、遅延なしで即時返却するか 1.0s ± 0.1s の遅延を適用するかで挙動の食い違いが発生し、実装者が混乱する原因となります。
   - 特にダミーセッション処理において非 active 時の評価で即時エラー返却が行われると、レスポンス時間の差異によってセッションの有効性やアカウントの存在が推測されるリスクが生じます。

## 3. 推奨される修正案
`02_auth.md` の 3.1.2, 3.1.7, 3.1.11 の「##### リクエスト評価順序」および「##### Errors」の記述を統合・統一してください。

ダミーセッションを含む無効/非 active ステータスセッションに対する Timing Attack 対策方針を明確化し、リクエスト評価順序と Errors セクションの遅延表記（即座返却か 1.0s ± 0.1s 遅延か）の不一致を解消してください。
