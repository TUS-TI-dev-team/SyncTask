# ユーザー管理APIにおけるリクエスト検証・認可・再認証処理の優先順位および評価順序の未定義

- **Status**: Resolved
- **Severity**: Medium
- **Created At**: 2026-08-17 16:45:00
- **Target Files**:
  - [03_users.md](docs/design/api_design/03_users.md)

## 1. 問題の概要
`DELETE users/{user_id}` (3.2.3) および `PATCH users/{user_id}/password` (3.2.4) において、リクエストボディ不正（`400 Bad Request`）、認可エラー（`404 Not Found`）、ビジネスルール違反（`422 SAME_AS_CURRENT_PASSWORD`）、パスワード再認証失敗（`401 REAUTH_FAILED`）など複数のエラーレスポンスが定義されています。
しかし、バックエンドにおける処理の評価順序（優先順位）が明記されていないため、実装において入力検証前に DB のパスワード比較や失敗カウンター更新を行ってしまうなどの仕様上の揺れが発生するリスクがあります。

## 2. 詳細な指摘内容
1. `3.2.3` および `3.2.4` では、リクエストパラメータの不備（例: `password` 未入力、`new_password` 要件違反）や、URL の `user_id` とセッションユーザーの不一致（BOLA/認可チェック）、現在のパスワード一致確認（再認証）がそれぞれ異なるエラーコード（400, 404, 422, 401）を返します。
2. もし入力バリデーション（400）や BOLA/認可チェック（404）より先にパスワード比較や失敗カウンター加算を実施してしまうと以下のセキュリティ上・実装上の問題が生じます：
   - 無効なリクエストボディ（形式不正等）の送信によって再認証失敗カウンター（`REAUTH_FAILED_COUNT`）が不当にカウントアップされ、アカウントロック/セッション破棄を引き起こすリスク。
   - 不要な bcrypt 等の高負荷ハッシュ比較処理が実行され、DoS 耐性やレスポンス特性に影響するリスク。
3. 400 Bad Request, 404 Not Found, 422 Unprocessable Entity が発生した際には Timing Attack 対策の固定遅延（`1.0s ± 0.1s`）や失敗カウンター更新は適用せず、即座にエラーを返却すべきですが、その評価順序が文書化されていません。

## 3. 推奨される修正案
`03_users.md` の 3.2.3 および 3.2.4 の説明（または `01_overview.md` の共通仕様部）に、リクエスト処理時の評価順序を明記してください。

**評価順序の明記例**:
```markdown
##### リクエスト評価順序
1. **リクエスト構文・入力バリデーション (`400 Bad Request`)**:
   リクエストボディの JSON 形式、必須フィールドの有無、および新パスワード等の文字数・文字種・禁止ワード検証を最優先で実施します。不備がある場合は即座に 400 エラーを返却します（遅延・失敗カウンター更新なし）。
2. **認可チェック・IDOR/BOLA検証 (`404 Not Found`)**:
   パスパラメータ `user_id` とセッションユーザーIDの一致を検証します。不一致またはユーザー非存在時は即座に 404 エラーを返却します（遅延・失敗カウンター更新なし）。
3. **ビジネスルール検証 (`422 Unprocessable Entity`)**:
   新パスワードが現在のパスワードと同一か等のチェックを実施します（遅延・失敗カウンター更新なし）。
4. **パスワード再認証検証 (`401 REAUTH_FAILED` / `SESSION_DESTROYED`)**:
   現在のパスワードのハッシュ照合を行います。不一致時は一律 `1.0s ± 0.1s` のレスポンス遅延を適用し、失敗回数をカウントアップして 401 エラーを返却します。
```

### 実施した修正内容
`03_users.md` の 3.2.3 (`DELETE users/{user_id}`) および 3.2.4 (`PATCH users/{user_id}/password`) に「リクエスト評価順序」セクションを追加し、1. 入力バリデーション (400) → 2. 認可検証 (404) → 3. ビジネスルール (422) → 4. パスワード再認証 (401) の順序を明確化しました。
