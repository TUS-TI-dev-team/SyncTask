# OTPセッション有効期間中のメールアドレス排他制御仕様の未記載

- **Status**: Resolved
- **Severity**: Medium
- **Created At**: 2026-08-17 15:01:00
- **Target Files**:
  - [api_design.md](docs/design/api_design.md)
  - [requirements.md](docs/req-def/requirements.md)
  - [database_design.md](docs/design/database_design.md)

## 1. 問題の概要
要件定義書には、OTPセッション有効期間中（初回発行から5分間、全体最大15分間）に、手続き中のメールアドレスに対する他ユーザーからの重複登録・変更リクエストを拒否（ダミーOTP処理対象）とし、認証確定または全体有効期限切れまで排他維持する旨が明記されている。しかし、API設計書の各 `request-otp` エンドポイント（3.1.1, 3.1.6, 3.1.10）にはこの排他制御の仕組みに関する記載がない。

## 2. 詳細な指摘内容
- **要件定義書 L33**: 「OTPセッション有効期間中（初回発行から5分間、再送信を含め全体最大15分間）は、作成予定のメールアドレスに対する他ユーザーからの重複登録・変更リクエストを拒否（ダミーOTP処理対象）とし、認証確定または全体有効期限切れまで排他維持する」
- **要件定義書 L49**: メールアドレス変更についても同様の排他維持要件が記載。
- **要件定義書 L201**: セキュリティ要件にて新規登録手続き中のメールアドレスへの排他制御を再確認。
- **DB設計書 L83, L198**: `OTP_SESSION.PENDING_EMAIL` を使用した排他判定インデックス `idx_otp_session_pending_email` が設計されており、DB設計書側では考慮済み。

API設計書ではダミーOTPセッション返却の仕組み自体は「既に登録済みのメールアドレスが指定された場合」に言及しているが、**「他ユーザーが手続き中（OTPセッション有効期間中）のメールアドレスが指定された場合」** の排他ケースについてはどのエンドポイントにも明示されていない。

このギャップにより、実装者が「既に登録済みのメールアドレス」のチェックのみを実装し、「他ユーザーの有効OTPセッションに紐づくメールアドレス」のチェックを見落とすリスクがある。

## 3. 推奨される修正案
各 `request-otp` エンドポイント（3.1.1, 3.1.6, 3.1.10）の仕様記述に、以下の排他ケースを追記する:

```
※指定されたメールアドレスが、他ユーザーのOTPセッション有効期間中（手続き中）のメールアドレスと一致する場合も、
既登録メールアドレスと同様にダミーOTPセッションを返却し `200 OK`（遅延 1.0s ± 0.1s）を返却します。
（参照: DB設計書 OTP_SESSION.PENDING_EMAIL による排他判定）
```

---

## 4. 修正完了報告

- **対応内容**: セクション 1.2 セキュリティおよび 3.1.1 `POST auth/register/request-otp` のダミー応答対象条件に、「他ユーザーの有効なOTPセッション保持期間中（手続き中）」の指定を追加・明記しました。
