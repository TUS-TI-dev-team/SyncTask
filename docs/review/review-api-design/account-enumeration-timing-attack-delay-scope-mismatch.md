# アカウント列挙防止における正常処理時とダミー応答時の遅延制御スコープの不整合

- **Status**: Resolved
- **Severity**: Major
- **Created At**: 2026-08-17 16:45:00
- **Target Files**:
  - [01_overview.md](docs/design/api_design/01_overview.md)

## 1. 問題の概要
`01_overview.md` 1.2 節の「アカウント列挙防止 (User Enumeration 対策)」および「遅延制御 (Timing Attack 対策)」において、`ダミーOTPセッションを発行して 200 OK（応答遅延 1.0s ± 0.1s）を返却` や `アカウント存在有無のダミー処理時は、一律 1.0s ± 0.1s のレスポンス遅延を適用します` と「ダミー処理時」に限定してレスポンス遅延が記述されている。
しかし、新規登録（`auth/register/request-otp`）、パスワードリセット（`auth/password-reset/request-otp`）、メールアドレス変更（`auth/change-email/request-otp`）等の OTP 発行処理において、実在するユーザーに対する正常成功応答時の遅延時間について明記されていない。正常成功処理が数10ms等の即時応答で処理された場合、レスポンス時間の差異からアカウントの存在有無が漏洩する脆弱性リスクがある。

## 2. 詳細な指摘内容
1. **Side-Channel（レスポンス時間差）によるアカウント列挙脆弱性**:
   - `01_overview.md` L30 や L37 では「ダミー処理時」における `1.0s ± 0.1s` のレスポンス遅延が規定されている。
   - もし実装者がこの記述に従い、未登録メールアドレスへの新規登録や実在ユーザーへのパスワードリセット成功時に遅延（`1.0s ± 0.1s`）を入れず即時レスポンスを返した場合、攻撃者は「即時返答＝実在アカウント/正常成功」「1.0秒後返答＝ダミーセッション（重複または手続き中）」であることを応答時間差から判別可能となる。
   - これにより、メッセージ内容やステータスコードを統一していても Timing Attack による Side-Channel 攻撃でアカウントの存在有無や状態が特定され、アカウント列挙防止対策が無効化する。

## 3. 推奨される修正案
`01_overview.md` 1.2 節の記述を「ダミー処理時」に限定せず、`request-otp` 系のすべての処理で正常成功・ダミー応答を問わず一律で遅延を適用する仕様へ補正してください。

```markdown
- **アカウント列挙防止 (User Enumeration 対策)**:
  - 新規登録（`auth/register/request-otp`）、パスワードリセット（`auth/password-reset/request-otp`）、メールアドレス変更（`auth/change-email/request-otp`）において、指定されたメールアドレスの登録有無、他ユーザーとの重複、現在と同一メールアドレスの指定、または他ユーザーの有効なOTPセッション期間中（手続き中）の指定にかかわらず、**正常成功時・ダミー発行時を一貫して区別せずレスポンス遅延（1.0s ± 0.1s）を適用した上で `200 OK` を返却**します。これにより、エラーコード・レスポンス構造・応答時間のあらゆる差異からメールアドレスの登録状況が推測されることを完全に防止します。
- **遅延制御 (Timing Attack 対策)**:
  - ログイン失敗、OTP発行処理（正常成功時およびアカウント存在有無のダミー処理時を含む一括）、OTP検証失敗、パスワード再認証失敗時は、一律 `1.0s ± 0.1s` のレスポンス遅延を適用します。
```
