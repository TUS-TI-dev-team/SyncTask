# タスク更新APIのHTTPメソッドセマンティクス不整合（PUT vs PATCH）

- **Status**: Open
- **Severity**: Minor
- **Created At**: 2026-08-17 15:01:00
- **Target Files**:
  - [api_design.md](docs/design/api_design.md)

## 1. 問題の概要
`PUT tasks/{task_id}`（3.3.4）は「リクエストボディに含まれるフィールドのみを部分更新する実質的な部分更新兼用仕様」と明記されているが、HTTPメソッドには `PUT` が使用されている。RFC 9110 において `PUT` はリソースの完全置換（リクエストにないフィールドはデフォルト値にリセットまたは削除）を意味し、部分更新は `PATCH` のセマンティクスに該当する。

## 2. 詳細な指摘内容
- **API設計書 L749-750**: 「全項目の一括更新に加え、リクエストボディに含まれるフィールドのみを部分更新（ステータス変更 `status` やピン留め `is_pinned` の単体更新含む）する実質的な部分更新兼用仕様」と記載。
- **API設計書 L768**: 「ステータスのみを変更する場合は `{"status": "completed"}`…のように、更新対象のフィールドのみを指定して送信可能」と記載。
- **API設計書 L772-779**: フィールド定義で全フィールドが「必須: ×」（任意）とされている。

この仕様は明確に部分更新（PATCH）のセマンティクスである。`PUT` を使用した場合、クライアントライブラリやAPIゲートウェイ、ドキュメント自動生成ツール等が `PUT` のセマンティクス（リソースの完全置換）を前提に動作し、未指定フィールドの扱いに混乱が生じる可能性がある。

特に、`title` を含めず `{"is_pinned": true}` のみを送信した場合、`PUT` のセマンティクスでは `title` が空/デフォルト値にリセットされると解釈されるリスクがある。

## 3. 推奨される修正案
以下のいずれかの対応を推奨する:

**案A（推奨）: HTTPメソッドを `PATCH` に変更**
```
#### 3.3.4 `PATCH tasks/{task_id}`
タスク情報を部分更新します。リクエストボディに含まれるフィールドのみが更新対象となります。
```

**案B: `PUT` を維持する場合はセマンティクスの注記を追加**
現在の `PUT` を維持する判断の場合は、未指定フィールドの扱い（変更なし）を明示的に注記し、RFC準拠のセマンティクスとの差異を明記する:
```
※本APIは `PUT` メソッドを使用していますが、リクエストボディに含まれないフィールドは変更せず既存値を維持します
（RFC 9110 における PUT の完全置換セマンティクスとは異なる部分更新仕様です）。
```
