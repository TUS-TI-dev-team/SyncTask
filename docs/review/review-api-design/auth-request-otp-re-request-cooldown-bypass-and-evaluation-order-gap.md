## 1. 問題の概要
`02_auth.md` の OTP 再送 API 群（3.1.3 `register/resend-otp`, 3.1.8 `password-reset/resend-otp`, 3.1.12 `change-email/resend-otp`）では、連続送信を防止するため 60 秒間のクールダウン制限（`429 OTP_RESEND_COOLDOWN`）が明記されています。しかし、初回発行 API 群（3.1.1 `register/request-otp`, 3.1.6 `password-reset/request-otp`, 3.1.10 `change-email/request-otp`）において、有効な `active` セッションが存在する状態で同一メールアドレスに対して再度 `request-otp` が呼び出された場合の処理挙動・クールダウン制御および「リクエスト評価順序」が定義されていません。

## 2. 詳細な指摘内容
1. **60秒クールダウン回避（バイパス）のリスク**:
   - クライアントが OTP 再送 API (`resend-otp`) を使わずに、同一メールアドレスで初回発行 API (`request-otp`) を短時間で繰り返し実行した場合の挙動が未定義です。
   - もし `request-otp` で既存の `active` セッションが存在してもクールダウンなしで新しい OTP セッションを発行・メール送信してしまう仕様であれば、`resend-otp` の 60 秒クールダウン制限（`429 OTP_RESEND_COOLDOWN`）を無効化・バイパスされるセキュリティホールとなります。
   - 逆に `request-otp` でも 60 秒クールダウンを適用または既存セッションを維持してダミー応答を返す仕様である場合、その旨が各 `request-otp` API の Errors 一覧（429 エラー等の記載なし）および解説に記載されていません。

2. **リクエスト評価順序の未定義**:
   - 3.1.1, 3.1.6, 3.1.10 のいずれのエンドポイントにも `##### リクエスト評価順序` が存在せず、IP レートリミット、入力バリデーション（400）、既存アクティブセッションチェック（429 または 200 ダミー応答）、および Timing Attack 対策用遅延（1.0s ± 0.1s）の適用順番が明確ではありません。

## 3. 推奨される修正案
`02_auth.md` の 3.1.1, 3.1.6, 3.1.10 に `##### リクエスト評価順序` セクションを追加し、以下の点を明記してください：
1. 既に該当メールアドレスに対する有効な `active` OTP セッションが存在する状態で短期間（60秒未満）に再度 `request-otp` が送信された場合の挙動（`429 OTP_RESEND_COOLDOWN` エラーを返却するか、ダミー応答として 200 OK + 遅延 1.0s ± 0.1s を返却してメール送信をスキップするか）。
2. リクエストバリデーション（400、即時返却・遅延なし）とアカウント列挙防止処理（200 OK、一律遅延 1.0s ± 0.1s 適用）の評価優先順序。
