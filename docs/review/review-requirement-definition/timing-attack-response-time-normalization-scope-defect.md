# タイミング攻撃防止を目的とした固定応答時間の適用範囲不備

- **Status**: Resolved
- **Severity**: Major
- **Created At**: 2026-08-13 21:37:30
- **Target Files**:
  - [requirements.md](docs/req-def/requirements.md)

## 1. 問題の概要
要件定義書において、タイミング攻撃（Timing Attack）防止およびユーザー存在秘匿を目的としたレスポンス遅延制御（1s±0.1s）が定義されていますが、その適用対象が「認証・検証失敗時」および「ダミー処理時」に限定されています。認証・検証が成功した場合の応答時間制御について明記されておらず、成功処理と失敗処理の間に応答速度の差が生じることで、ユーザー存在確認や認証状態の推測が可能となるセキュリティ上の脆弱性および要件上の矛盾が存在します。

## 2. 詳細な指摘内容
`docs/req-def/requirements.md` の以下の箇所に記載があります：

- **L142**: `論理削除アカウントでのログイン試行時は、一般的な「メールアドレスまたはパスワードが正しくありません」として認証を拒否し、論理削除の有無を秘匿する（応答遅延 1s±0.1s）`
- **L146**: `ロックアウト期間中（30分間）のログイン試行は、正しいパスワードが入力された場合であっても認証拒否（1s±0.1s遅延）とする`
- **L152**: `ダミーOTP入力画面での誤入力検証は常に失敗扱い（応答速度1s±0.1s）とし、メールアドレスの登録有無を秘匿する`
- **L203-L204**:
  ```markdown
  - 検証・認証失敗時の応答速度を1s±0.1sの範囲で調整する
  	- タイミング攻撃防止のため，処理の成否をユーザに判断させないために行う
  ```

### 仕様上の不備：
L204 では「タイミング攻撃防止のため，処理の成否をユーザに判断させないために行う」と目的が明記されています。
しかし、L203 の定義では適用対象が「検証・認証失敗時」に絞られています。
仮に認証・検証が「成功」した場合に人工的な遅延を挟まず即時レスポンス（例: 30ms〜50ms）を返す実装となった場合、攻撃者はレスポンス時間の違いを測定することで以下を容易に推測できてしまいます：
1. **ログイン時**: 成功（高速レスポンス）か失敗（1秒遅延）かにより、パスワードの正誤およびメールアドレスの存在を識別できる。
2. **OTP検証時**: 正しいOTPを入力した際（高速レスポンス）と誤ったOTPを入力した際（1秒遅延）でレスポンス時間により正解OTPをサイドチャネル攻撃で特定できる。
3. **新規登録・パスワードリセット・メールアドレス変更のOTP要求時**: 実在するアドレスへのOTP発行処理（メール送信等の非同期処理を含む高速レスポンス）とダミー処理（1秒遅延）でメールアドレスの登録有無を識別できる。

したがって、「失敗時のみ1秒遅延させる」仕様では、目的である「処理の成否を判定させない（タイミング攻撃防止）」を達成できません。

## 3. 推奨される修正案
`docs/req-def/requirements.md` の「脆弱性対策」または「セキュリティ」セクションにおける応答時間制御の規定（L203-L204）を、成功・失敗・ダミー処理を問わず一律に適用するよう以下のように更新してください：

```markdown
- 検証・認証処理の応答速度を、処理の成否（成功・失敗）およびダミー処理の有無を問わず、一律1s±0.1sの範囲に正規化（レスポンス遅延調整）する
	- ログイン認証、OTP検証、アカウント登録・パスワードリセット・メールアドレス変更のOTP発行/再送依頼等の認証系エンドポイントにおいて、処理結果による応答時間の差分を利用したユーザー列挙およびタイミング攻撃を防止するために行う
```

## 修正完了報告

- **Resolved At**: 2026-08-13 21:53:00
- **Status**: Resolved

### 実施した修正内容
ヒアリングにて確定した方針（「OTP認証およびログイン処理について、失敗またはダミー処理の場合は一律 1s±0.1s 待ち、成功時は即座に次の処理に移る方針を採用する」）に基づき、`docs/req-def/requirements.md` のセキュリティ要件を更新しました。失敗またはダミー処理時の遅延調整（1s±0.1s）と、成功時の即時レスポンス挙動について明記し仕様の曖昧さを解消しました。
