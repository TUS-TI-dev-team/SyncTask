# バックエンド テストコード作成ガイド (Backend Testing Guide)

このドキュメントでは、SyncTask バックエンド（Go / Gin / PostgreSQL / Supabase）における**テストの基本方針・規約**を解説します。

---

## 必須事項

### 1. ファイル配置と命名規約
- **ファイル配置**: Go 標準規約に従い、テスト対象ファイルと同一ディレクトリに `<対象ファイル名>_test.go` として配置します。
- **パッケージ宣言**: 原則としてテスト対象と同一パッケージ名（例: `package handler`）を指定します。
- **テスト関数名**: `Test<関数名>` または `Test<関数名>_<シナリオ>`
- **サブテスト名 (`t.Run`)**: 日本語で「`<分類>: <期待される結果>`」の形式で記述します。
  - 分類プレフィックス: `正常系:`, `異常系:`, `境界値:`, `準正常系:`

```go
func TestValidateTaskTitle(t *testing.T) {
	t.Run("正常系: 有効なタイトルの場合に検証を通過すること", func(t *testing.T) { ... })
	t.Run("異常系: 空文字の場合は ErrEmptyTitle を返すこと", func(t *testing.T) { ... })
	t.Run("境界値: 最大長 100 文字の場合に通過すること", func(t *testing.T) { ... })
}
```

### 2. Code-as-Docs の基本方針
SyncTask では**「コードとテスト自体が仕様書になる」**という方針を採用しています。
1. **実装コード**: GoDoc コメントに `@spec` を記載し、事前条件・事後条件・エラー仕様を明記する。
2. **テストコード**: `t.Run` のサブテスト名に `@spec` の各項目に対応する仕様文を日本語で記述する。

### 3. アサーション原則 (`require` vs `assert`)
- **`require` (即時中断)**: その後の検証でパニックを起こす可能性がある前提条件（`err == nil`、戻り値ポインタの非 nil、スライスの長さチェック等）。
- **`assert` (検証継続)**: 各プロパティ値やステータスコードの比較。失敗しても以降のアサーションを継続して差分を可視化します。

```go
require.NoError(t, err)  // エラー時はここで中断
require.NotNil(t, res)   // nil の場合は中断
assert.Equal(t, 200, res.StatusCode)
assert.Equal(t, "ok", res.Status)
```

### 4. テストの独立性 (Isolation)
- 各テストケースは他のテストの実行順序や状態に依存してはなりません。
- グローバル変数や `gin.SetMode` を変更した場合は、テスト終了時に必ず元の状態に戻してください。

### 5. 基本のテスト実行コマンド

```bash
# バックエンドディレクトリ (backend/) で実行

# 全テストを実行
go test ./...

# 詳細な結果を表示 (Verbose)
go test -v ./...

# カバレッジを測定
go test -cover ./...
```
